1. O que é o Hórus (em 1 minuto)

O Hórus é um sistema que cruza bases de dados públicas brasileiras para descobrir irregularidades que ninguém vê quando olha as bases isoladamente. A ideia é simples: cada portal do governo (Portal da Transparência, Receita, TSE, CEIS, TCU, Diário Oficial) é um pedaço de quebra-cabeça. Sozinhos, eles não dizem muita coisa. Juntos, denunciam o que está errado.

📌 Exemplo do mundo real (descoberto hoje pelo sistema)
A empresa ATIVA TERCEIRIZACAO LTDA está no CEIS (Cadastro de Empresas Inidôneas e Suspensas) — ou seja, foi oficialmente proibida de fazer negócio com o governo. Ainda assim, a base de contratos federais mostra que ela tem R$ 2,3 milhões em contrato com o Ministério da Saúde. Esse é o tipo de furo que o Hórus detecta automaticamente, e é o exemplo mais limpo do porquê a fragmentação entre portais públicos permite que irregularidades passem despercebidas.

🧠 Leitura desse desenho para um leigo
De cima pra baixo, é um funil:
  1. O governo expõe APIs com dados públicos.
  2. O módulo de ingestão chama essas APIs e traduz cada item para o nosso modelo de tabelas.
  3. O banco PostgreSQL armazena tudo organizado, com relações entre as tabelas.
  4. O módulo de analítica analisa os dados de duas formas: regras explícitas (score) e aprendizado de máquina (Isolation Forest).
  5. Os routers expõem esses resultados como endpoints HTTP, e o Swagger UI deixa qualquer pessoa testar pelo navegador, sem precisar saber programar.

4. O que foi feito hoje (06/05/2026)

Cinco grandes blocos de trabalho, na ordem em que aconteceram:

1

Subir a infraestrutura

Os containers do Hórus (banco e Redis) estavam parados. Subimos com:

docker compose up -d

Resultado: horus-db (PostgreSQL na porta 5433) e horus-redis (porta 6380) ficaram healthy.

2

Validar a chave da API da CGU

Você cadastrou em portaldatransparencia.gov.br/api-de-dados/cadastrar e colocou no backend/.env a variável API_PORTAL_TRANSPARENCIA_KEY. A API exige essa chave em todo header chave-api-dados. Sem ela, devolve 401 Unauthorized.

3

Disparar ingestão real do CEIS

Chamamos POST /ingestao/ceis?paginas=5. O sistema:

  • Bateu na API da CGU (5 páginas × 15 itens = 75 registros brutos)
  • Pulou pessoas físicas (modelo atual só armazena empresas)
  • Para cada CNPJ novo, criou a empresa no banco (upsert) e gravou o registro de sanção
  • Recalculou os scores

Resultado: 26 empresas sancionadas inseridas (somadas a 18 já existentes de antes = 44 sanções reais + 31 PFs puladas).

4

Criar a "outra ponta" do cruzamento 5

Saber que uma empresa está no CEIS é só metade da história. A outra metade é: ela ainda tem contrato federal ativo? Implementamos:

  • buscar_contratos_por_cnpj() — usa o endpoint /contratos/cpf-cnpj da CGU
  • ingerir_contratos_de_sancionados() — percorre cada empresa do CEIS no banco, chama a API e persiste os contratos encontrados
  • POST /ingestao/contratos-de-sancionados — endpoint HTTP que dispara isso

Disparamos para 20 empresas → 38 contratos federais reais ingeridos. 5 das 20 empresas tinham contrato (25%) — e cada um desses é uma irregularidade direta.

Para isso foi necessário aumentar a coluna contratos_publicos.id de VARCHAR(10) para VARCHAR(20) (os IDs da CGU são longos).

5

Implementar o Isolation Forest

O edital de PI III exige ciência de dados obrigatoriamente. O score que já existia é determinístico — apenas regras tipo "se isso e aquilo, soma 30 pontos". Adicionamos um modelo estatístico que aprende o que é "normal" e aponta o que foge da curva, mesmo quando nenhuma regra dispara.

Algoritmo: Isolation Forest do scikit-learn — não-supervisionado, ideal pra detecção de anomalias quando você não tem rótulos.

Features (variáveis usadas):

  1. num_contratos
  2. valor_total_contratos
  3. valor_max_contrato
  4. num_orgaos_distintos
  5. num_socios
  6. num_sancoes_ceis
  7. num_doacoes_realizadas

Endpoints: POST /ml/treinar (fit + persistência em joblib) e GET /ml/anomalias (carrega modelo e aponta as N mais atípicas).

Resultado: 15 anomalias detectadas em 144 empresas (com contamination=0.1).

8. Isolation Forest — o "ML" do projeto, explicado simples

🤔 Para que serve, em uma frase?

Apontar empresas que estão estatisticamente fora do padrão mesmo quando nenhuma regra fixa dispara. É um detector de "isso aqui está estranho, vai que o avaliador humano olha".

⚙️ Como funciona, em uma analogia

Imagine que você joga 200 empresas em uma floresta de árvores aleatórias. Cada árvore tenta "isolar" cada empresa fazendo perguntas binárias (valor maior que X? número de órgãos maior que Y?...). Empresas normais precisam de muitas perguntas pra serem isoladas (ficam "no meio do bolo"). Empresas anômalas são isoladas com poucas perguntas (têm valores extremos). O algoritmo mede isso e pontua.

🏆 Top 3 anomalias detectadas hoje

#EmpresaScorePor que ficou estranha
1 MATOS EQUIPAMENTOS HOSPITALARES LTDA -0.151 Combo raro: poucos contratos (3) mas valor alto (R$ 13,6 mi), em 3 órgãos diferentes, com 1 sanção CEIS e 1 doação
2 ATIVA TERCEIRIZACAO LTDA -0.128 Nome real do CEIS — 15 contratos federais (volume alto) com 0 sócios cadastrados (suspeito) e suspensa
3 PINTO TECNOLOGIA ME -0.116 3 contratos somando R$ 14,9 mi (ticket médio enorme), 0 sócios e doadora eleitoral
💡 O ponto-chave do ML neste projeto
O Isolation Forest complementa o score determinístico — ele captura padrões que as regras não enxergam. O caso da BARROS COMÉRCIO (não está nas top 3 mas apareceu nas 15 anomalias) é o exemplo perfeito: empresa com zero contratos e três doações eleitorais. Nenhuma regra do score determinístico pega isso, porque o score só penaliza quem ganhou contrato. O ML pega.
